# 상품 이미지 저장소 설계 (Supabase Storage) v2

## 결정 사항

| 항목 | 값 | 상태 |
|---|---|---|
| 버킷 | `product-images` (public: 보기만 공개) | 설계 승인 |
| 허용 형식 | `image/jpeg`, `image/png`, `image/webp` | ✅ 승인 |
| 최대 크기 | 파일당 5MB (`5242880` bytes) | ✅ 승인 |
| 매직 바이트 검사 | 업로드 직후 + 저장 시 | ✅ 승인 |
| 버킷 전체 800MB | **소프트 한도** (강제 아님, 아래 참고) | 조건부 |
| 파일 경로 | `products/<랜덤 uuid>.<jpg|png|webp>` | |
| DB 저장 값 | 경로만 저장 (`products.image_path`) | |
| 이미지 수 | 상품당 1장 (다중 이미지는 Phase 8) | |

SQL: [20261109000002_create_product_images_bucket.sql](../../supabase/migrations/20261109000002_create_product_images_bucket.sql) (DB 적용 전, 승인 필요)

## 왜 "signed upload URL" 방식인가

| 방식 | 문제 |
|---|---|
| 브라우저 → Server Action으로 파일 전송 | Vercel 함수는 요청 본문이 **4.5MB로 제한**되어 5MB 파일이 실패한다. Next.js Server Action의 기본 한도도 1MB이다. |
| 브라우저가 공개 키로 직접 업로드 | 누구나 업로드할 수 있도록 Storage 정책을 열어야 한다. |
| **서버가 1회용 업로드 URL 발급 → 브라우저가 Storage로 직접 업로드** ✅ | 서버가 형식과 크기를 먼저 검사하고, 정해진 경로 하나에만 업로드를 허용한다. 파일이 Vercel을 거치지 않는다. |

## 강제되는 제한 vs 참고용 제한

| 제한 | 누가 강제하나 | 보장 |
|---|---|---|
| 파일당 5MB | Storage 서버 (버킷 설정) | ✅ 우회 불가 |
| Content-Type이 JPEG/PNG/WebP | Storage 서버 (버킷 설정) | ✅ 단, 업로드할 때 보내는 "선언값" 기준 |
| 실제 내용이 이미지인지 | Next.js 서버의 매직 바이트 검사 | ✅ 상품에 연결되기 전에 반드시 통과해야 함 |
| 다른 파일 덮어쓰기 금지 | 서버가 경로 결정 + `upsert: false` | ✅ |
| 버킷 전체 800MB | 업로드 URL 발급 직전 사용량 확인 | ⚠️ **소프트 한도**: 동시에 발급된 URL 수 × 5MB만큼 넘을 수 있음 |
| 버킷 전체 용량 (고아 파일 포함) | 없음 | ❌ **보장 안 됨** → 아래 "용량 관리" 참고 |

> 상품 개수 제한(300개, DB가 강제)과 Storage 용량은 **별개의 문제**로 관리합니다.
> 상품 수를 줄여도 상품에 연결되지 않은 파일(고아 파일)은 계속 쌓일 수 있으므로, 용량 보장 수단이 되지 않습니다.

## 용량 관리 (상품 수 제한과 별개)

### 파일이 남는 경로와 정리 여부

| 경로 | 정리 방식 | 남을 수 있나 |
|---|---|---|
| 상품 삭제 | DB 삭제 성공 → 연결 파일 삭제 | 파일 삭제 실패 시에만 (로그 기록) |
| 이미지 교체 (수정) | DB 수정 성공 → 이전 파일 삭제 | 위와 같음 |
| 이미지 제거 (수정) | DB 수정 성공 → 기존 파일 삭제 | 위와 같음 |
| 업로드 후 매직 바이트 검사 실패 | 즉시 삭제 | 삭제 실패 시에만 |
| Storage 업로드 자체 실패 | 파일이 생기지 않음 | 없음 |
| 저장 전 이미지 교체·제거 | `discardImageUpload`로 삭제 | 요청 실패 시 |
| **업로드 후 폼을 버리고 나감** | 없음 | **남음** |
| **업로드 URL만 받고 실제 상품 저장은 안 하는 반복 요청 (악용)** | 없음 | **남음, 누적 가능** |

### 동시 업로드에서 800MB 검사가 부정확한 이유
1. 검사는 **URL을 발급하는 시점**에 하고, 실제 업로드는 그 뒤(최대 2시간 이내)에 일어난다.
2. 누군가 URL을 한꺼번에 많이 받아두면 모두 "현재 사용량 0MB" 기준으로 통과한다. 예: URL 1,000개 × 5MB = 5GB.
3. 그래서 현재 설계는 **악용을 막는 장치가 아니라, 정상 사용 중 용량이 서서히 차는 것을 알리는 경고 장치**다.

### 정확하게 만들려면 (선택 작업 · 필수 CRUD 이후)
- **업로드 예약 방식**: URL을 발급할 때 DB에 "5MB 예약"을 기록하고, `실제 사용량 + 유효한 예약 합계 ≤ 800MB`를 잠금 안에서 검사한다. 예약은 상품 저장, 폐기, 2시간 만료 시 해제한다. 이렇게 하면 동시 요청에서도 한도를 넘지 않는다.
- **고아 파일 정리**: DB에 연결되지 않았고 2시간이 지난 파일을 삭제하는 정리 작업 (수동 실행 스크립트 또는 Supabase Cron)
- 이 두 가지는 미션 필수 범위가 아니므로, 상품 CRUD와 이미지 업로드를 완성한 뒤 별도 승인을 받아 진행한다.

## 업로드 흐름

```
[브라우저]                                 [Next.js 서버]                       [Supabase Storage]
1. 파일 선택
2. 형식·크기 1차 검사, 미리보기
3. ── requestImageUpload({type, size}) ──▶
                                     4. 형식·크기 재검사, 사용량 확인(소프트)
                                     5. 경로 products/<uuid>.<ext> 결정
                                     6. createSignedUploadUrl(path)
   ◀──────────────── { path, token } ──
7. uploadToSignedUrl(path, token, file) ────────────────────────────────▶ 8. 5MB·Content-Type 검사
9. ── verifyImageUpload(path) ─────────▶
                                    10. 파일 앞 16바이트를 읽어 매직 바이트 확인
                                        + 경로 확장자와 실제 형식 일치 확인
                                        실패 → 파일 즉시 삭제 → 오류 반환
   ◀──────────── { ok } 또는 { error } ──
11. ok면 숨김 필드 image_path = path, [저장] 활성화
12. [저장] ── createProduct / updateProduct ──▶
                                    13. zod 검증 → 매직 바이트 **재검사**
                                        (9번을 건너뛰고 경로만 보내는 요청 대비)
                                    14. DB 저장
```

**매직 바이트 기준**

| 형식 | 파일 시작 바이트 | 경로 확장자 |
|---|---|---|
| JPEG | `FF D8 FF` | `.jpg` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `.png` |
| WebP | `52 49 46 46`(RIFF) + 4바이트 + `57 45 42 50`(WEBP) | `.webp` |

## 실패 상황별 처리 (파일 정리 포함)

| # | 상황 | 파일 상태 | 서버 처리 | 화면 안내 |
|---|---|---|---|---|
| 1 | 브라우저 1차 검사 실패 (형식, 크기) | 없음 | 요청 안 함 | "JPEG, PNG, WebP 파일만 올릴 수 있습니다" / "5MB 이하 파일만 올릴 수 있습니다" |
| 2 | 업로드 URL 발급 거부 (형식·크기·사용량) | 없음 | 정리할 것 없음 | 이유에 맞는 문구 |
| 3 | Storage 업로드 실패 (네트워크, 413, 415) | 없음 (업로드는 전부 성공하거나 전부 실패) | 정리할 것 없음 | "이미지 업로드에 실패했습니다" + [다시 시도] |
| 4 | **업로드 성공 → 매직 바이트 검사 실패** | 생성됨 | **즉시 삭제** 후 오류 반환. 삭제도 실패하면 경로를 서버 로그에 `orphan` 표시로 기록 | "이미지 파일이 손상되었거나 지원하지 않는 형식입니다. 다른 파일을 선택해 주세요" + 미리보기 제거 |
| 5 | 업로드 성공 → 검사 요청 자체 실패 (네트워크) | 생성됨 (검증 전) | 없음 | "이미지 확인에 실패했습니다" + [다시 확인]. **확인 전까지 [저장] 비활성화** |
| 6 | 검증된 이미지를 사용자가 제거하거나 다른 파일로 교체 (저장 전) | 생성됨 | `discardImageUpload(path)`: **DB의 어떤 상품도 이 경로를 쓰지 않을 때만** 삭제 | 조용히 처리 |
| 7 | 이미지는 정상인데 상품 저장 실패 (SKU 중복 등) | 생성됨 | 파일 유지 | 입력값과 이미지 유지 → 고친 뒤 다시 저장 (재업로드 불필요) |
| 8 | 저장 시 재검사 실패 (경로 조작, 파일 없음) | — | DB 저장 안 함. 해당 경로가 미사용 파일이면 삭제 | 이미지 칸 오류 |
| 9 | 업로드 후 폼을 버리고 나감 | 생성됨 | 남음 (고아 파일) | — |

**고아 파일(어떤 상품에도 연결되지 않은 파일)**: 4번과 6번의 삭제 실패, 9번에서 생깁니다. 데모 규모에서는 허용하고, Phase 8에서 "DB에 없고 2시간이 지난 파일 정리" 작업을 추가합니다.

## 저장 후 파일 정리 규칙

| 상황 | 처리 |
|---|---|
| 수정에서 이미지 교체 | DB를 새 경로로 UPDATE **성공 후** 이전 파일 삭제 |
| 수정에서 이미지 제거 | DB `image_path = null` 성공 후 기존 파일 삭제 |
| 상품 삭제 | DB DELETE ... RETURNING image_path 성공 후 파일 삭제 |
| 위의 파일 삭제가 실패 | 상품 처리는 성공으로 유지하고 서버 로그에 경로를 기록 |

> 원칙: **DB가 먼저, 파일 삭제는 나중.** 순서가 반대면 DB 저장이 실패했을 때 상품이 없는 이미지를 가리키게 된다.

## 표시

- `{SUPABASE_URL}/storage/v1/object/public/product-images/{path}`를 `next/image`로 보여준다. `images.remotePatterns`에 Supabase 도메인을 등록한다.
- 경로가 없거나 이미지를 불러오지 못하면 기본 플레이스홀더를 보여준다.

## 보안

- 업로드 URL은 서버만 발급하고, 경로도 서버가 정한다. 덮어쓰기는 금지한다.
- `storage.objects`에는 공개 정책이 없다. 공개 키로는 업로드, 삭제, 목록 조회를 할 수 없다.
- `image_path`는 그대로 믿지 않는다. 형식 검사와 매직 바이트 재검사를 거치고, DB UNIQUE 제약으로 다른 상품의 이미지를 가로챌 수도 없다.
- `discardImageUpload`는 상품에 연결된 파일을 절대 지우지 않는다.
- 데모 이미지만 올리도록 안내한다.
