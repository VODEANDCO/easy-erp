## 왜 "signed upload URL" 방식인가

| 방식 | 문제 |
|---|---|
| 브라우저 → Server Action으로 파일 전송 | Vercel 함수는 요청 본문이 **4.5MB로 제한**되어 5MB 파일이 실패한다. Next.js Server Action의 기본 한도도 1MB이다. |
| 브라우저가 공개 키로 직접 업로드 | 누구나 업로드할 수 있도록 Storage 정책을 열어야 한다. |
| **서버가 1회용 업로드 URL 발급 → 브라우저가 Storage로 직접 업로드** ✅ | 서버가 형식과 크기를 먼저 검사하고, 정해진 경로 하나에만 업로드를 허용한다. 파일이 Vercel을 거치지 않는다. |

## 강제되는 제한 vs 참고용 제한

| 제한 | 누가 강제하나 | 보장 |
|---|---|---|
| 파일당 5MB | Storage 서버 (버킷 설정) | ✅ 우회 불가 |
| Content-Type이 JPEG/PNG/WebP | Storage 서버 (버킷 설정) | ✅ 단, 업로드할 때 보내는 "선언값" 기준 |
| 실제 내용이 이미지인지 | Next.js 서버의 매직 바이트 검사 | ✅ 상품에 연결되기 전에 반드시 통과해야 함 |
| 다른 파일 덮어쓰기 금지 | 서버가 경로 결정 + `upsert: false` | ✅ |
| 버킷 전체 800MB | 업로드 URL 발급 직전 사용량 확인 | ⚠️ **소프트 한도**: 동시에 발급된 URL 수 × 5MB만큼 넘을 수 있음 |
| 버킷 전체 용량 (고아 파일 포함) | 없음 | ❌ **보장 안 됨** → 아래 "용량 관리" 참고 |

> 상품 개수 제한(300개, DB가 강제)과 Storage 용량은 **별개의 문제**로 관리합니다.
> 상품 수를 줄여도 상품에 연결되지 않은 파일(고아 파일)은 계속 쌓일 수 있으므로, 용량 보장 수단이 되지 않습니다.

## 용량 관리 (상품 수 제한과 별개)

### 파일이 남는 경로와 정리 여부

| 경로 | 정리 방식 | 남을 수 있나 |
|---|---|---|
| 상품 삭제 | DB 삭제 성공 → 연결 파일 삭제 | 파일 삭제 실패 시에만 (로그 기록) |
| 이미지 교체 (수정) | DB 수정 성공 → 이전 파일 삭제 | 위와 같음 |
| 이미지 제거 (수정) | DB 수정 성공 → 기존 파일 삭제 | 위와 같음 |
| 업로드 후 매직 바이트 검사 실패 | 즉시 삭제 | 삭제 실패 시에만 |
| Storage 업로드 자체 실패 | 파일이 생기지 않음 | 없음 |
| 저장 전 이미지 교체·제거 | `discardImageUpload`로 삭제 | 요청 실패 시 |
| **업로드 후 폼을 버리고 나감** | 없음 | **남음** |
| **업로드 URL만 받고 실제 상품 저장은 안 하는 반복 요청 (악용)** | 없음 | **남음, 누적 가능** |

### 동시 업로드에서 800MB 검사가 부정확한 이유
1. 검사는 **URL을 발급하는 시점**에 하고, 실제 업로드는 그 뒤(최대 2시간 이내)에 일어난다.
2. 누군가 URL을 한꺼번에 많이 받아두면 모두 "현재 사용량 0MB" 기준으로 통과한다. 예: URL 1,000개 × 5MB = 5GB.
3. 그래서 현재 설계는 **악용을 막는 장치가 아니라, 정상 사용 중 용량이 서서히 차는 것을 알리는 경고 장치**다.

### 정확하게 만들려면 (선택 작업 · 필수 CRUD 이후)
- **업로드 예약 방식**: URL을 발급할 때 DB에 "5MB 예약"을 기록하고, `실제 사용량 + 유효한 예약 합계 ≤ 800MB`를 잠금 안에서 검사한다. 예약은 상품 저장, 폐기, 2시간 만료 시 해제한다. 이렇게 하면 동시 요청에서도 한도를 넘지 않는다.
- **고아 파일 정리**: DB에 연결되지 않았고 2시간이 지난 파일을 삭제하는 정리 작업 (수동 실행 스크립트 또는 Supabase Cron)
- 이 두 가지는 미션 필수 범위가 아니므로, 상품 CRUD와 이미지 업로드를 완성한 뒤 별도 승인을 받아 진행한다.

## 업로드 흐름

```
[브라우저]                                 [Next.js 서버]                       [Supabase Storage]
1. 파일 선택
2. 형식·크기 1차 검사, 미리보기
3. ── requestImageUpload({type, size}) ──▶
                                     4. 데모 모드 → 업로드 스위치 → 폐기 서명 키 확인
                                        형식·크기 재검사, 미연결 파일 상한(20)·사용량(800MB) 확인 (읽기 전용)
                                     5. 경로 products/<uuid>.<ext> 결정
                                     6. createSignedUploadUrl(path, { upsert: false }) + discardKey 서명
   ◀────────── { path, token, discardKey } ──
7. uploadToSignedUrl(path, token, file) ────────────────────────────────▶ 8. 5MB·Content-Type 검사
9. ── verifyImageUpload(path) ─────────▶
                                    10. 서명 URL 로 앞 16바이트 범위 요청 (Range: bytes=0-15)
                                        206 + Content-Range(0번째부터, 전체 크기) + 응답 길이 확인
                                        → 정상 처리되지 않으면 info() 로 5MB 이하 확인 후 download()
                                        매직 바이트와 경로 확장자 일치 확인
                                        내용 불일치·크기 초과 → 파일 즉시 삭제 (미연결일 때만)
                                        시간 초과·네트워크 오류 → "확인 실패" (파일 삭제 안 함)
   ◀──────────── { ok } 또는 { error } ──
11. ok면 image_path = path, [저장] 활성화 (업로드·확인 중·실패 상태에서는 [저장] 비활성)
    저장 전에 다른 파일로 바꾸거나 [제거]·[되돌리기]·화면 이탈 → discardImageUpload({ path, discardKey }) (5-B)
12. [저장] ── createProduct / updateProduct ──▶
                                    13. zod 검증 → 존재·크기·매직 바이트 **재검사**
                                        (9번을 건너뛰고 경로만 보내는 요청 대비 · 확인 실패 시 저장 안 함)
                                    14. DB 저장 (unique(image_path) 로 중복 연결 차단)
                                    15. (수정) DB 성공 후 이전 이미지 정리 (5-B)
```

## 수정 시 이미지 처리 (5-B 구현)

```
폼이 보내는 image_path = "저장 후 원하는 이미지" ("" = 이미지 없음)
① 데모 모드 → zod → updated_at 형식
② 현재 이미지 읽기: SELECT image_path WHERE id = ? AND updated_at = ?   ← 이전 경로는 폼이 아니라 DB 에서 읽음
     0행 → NOT_FOUND / CONFLICT 구분 (파일 작업 없음)
③ 원하는 값 = 현재 값 → image_path 는 UPDATE 에 넣지 않음 (기존 수정 동작과 동일)
   원하는 값 = 새 경로 → 저장 직전 재검증 (실패·시간 초과 시 저장 안 함)
   원하는 값 = ""      → 이미지 제거
④ UPDATE ... WHERE id = ? AND updated_at = ?   (수정 충돌 검사 유지 · 0행이면 파일 작업 없음)
⑤ 성공한 뒤에만 이전 이미지 removeUnusedImage (어떤 상품도 쓰지 않을 때만 · 실패해도 수정은 유지, orphan 로그)
```

- 화면의 [제거]는 표시만 바꾸고 아무 파일도 지우지 않습니다. 실제 삭제는 저장이 성공한 뒤 서버가 합니다.
- 원래 저장된 이미지는 화면의 폐기 대상이 아닙니다. 폐기 대상은 "이 화면에서 새로 올렸고 아직 저장되지 않은 파일"뿐입니다.

## 폐기 서명과 환경변수 (5-B 구현)

| 항목 | 내용 |
|---|---|
| 목적 | 업로드 허가를 받은 브라우저 탭만 "그 경로의 저장 전 업로드"를 폐기할 수 있게 함. **용도는 폐기 하나뿐** (상품 등록·수정·삭제나 다른 파일 권한으로 쓰이지 않음) |
| 서명 | HMAC-SHA256. 서명 대상 `v1` · `discard` · 이미지 경로 · 만료 시각(초). `discardKey = "<만료시각>.<서명>"` |
| 만료 | 발급 후 24시간. 만료 후 폐기 거부 (파일은 남음 = 안전한 방향) |
| 비교 | `timingSafeEqual` |
| 폐기 검증 순서 | ① 데모 모드 → ② 입력 형태 → ③ 경로 형식 → ④ 서명(형식·만료·HMAC) → ⑤ `removeUnusedImage` (DB 에 연결된 파일은 삭제 안 함, 연결 확인 실패·시간 초과 시 삭제 안 함) |
| 응답 | ② 이후는 결과와 관계없이 같은 응답. 거부 사유만 서버 로그에 기록 (경로·서명값·키는 기록하지 않음) |
| 키 없음·짧음 | 업로드 허가 자체를 발급하지 않음 (fail-closed · 폐기할 수 없는 파일이 생기지 않게) |
| 키 교체 | 이전 서명이 모두 무효 → 저장 전 파일은 폐기되지 않고 남음. 상품에 연결된 이미지는 영향 없음 |

| 환경변수 (서버 전용, `NEXT_PUBLIC_` 금지) | 값 | 없을 때 |
|---|---|---|
| `PRODUCTS_IMAGE_UPLOAD_ENABLED` | 정확히 `true` | 업로드 꺼짐 |
| `PRODUCTS_IMAGE_DISCARD_SECRET` | 무작위 32바이트 이상 base64url(43자 이상). **Supabase 키와 별개**, 사용자가 직접 생성 | 업로드 꺼짐 |

로컬: 터미널 환경변수 또는 `.env.local` (사용자가 직접 설정). 배포: Vercel 환경변수. 값은 채팅·문서·GitHub 에 남기지 않습니다.

## 업로드 제한 장치 (5-A 구현)

로그인과 사업장 권한이 없는 현재 구조에서 업로드를 제한하는 방법입니다.

| 장치 | 내용 | 한계 |
|---|---|---|
| 데모 모드 | `PRODUCTS_DEMO_MODE` 가 정확히 `true` 가 아니면 업로드 Action 이 `FORBIDDEN` | — |
| 업로드 스위치 | `PRODUCTS_IMAGE_UPLOAD_ENABLED` 가 정확히 `true` 일 때만 발급 (기본 꺼짐). 상품 등록·수정·삭제는 그대로 두고 업로드만 끌 수 있음 | 서버 재시작(재배포) 필요 |
| 미연결 파일 상한 | 어떤 상품에도 연결되지 않은 파일이 20개 이상이면 발급 거부 (최대 약 100MB). **읽기 전용으로 세기만 하고 지우지 않음** | 동시 요청은 같은 개수를 볼 수 있어 몇 개 넘을 수 있음. 사용자 구분이 없어 한 사람이 상한을 채우면 업로드가 일시 중단됨 (데이터 피해는 없음) |
| 800MB 소프트 한도 | 발급 직전 `product_images_usage_bytes()` 확인 | 동시 발급분만큼 넘을 수 있음 |
| 요청 횟수 제한 | **없음** (SQL 003 초안 보류) | 배포 전 결정 항목 |

## 시간 제한과 fail-closed (5-A 구현)

Storage 단계마다 시간 제한을 두고, 넘으면 "이미지 확인에 실패했습니다"로 끝냅니다. **시간 초과·네트워크 오류로는 파일을 지우지 않고, 등록도 저장하지 않습니다.**

| 단계 | 제한 | 실제 요청 취소 (storage-js 2.119 기준) |
|---|---|---|
| 범위 요청 (`fetch`) | 5초 | ✅ `AbortController` |
| `download()` (대체 방식) | 10초 | ✅ `signal` |
| `list()` (미연결 개수) | 8초 | ✅ `signal` |
| DB 조회·`rpc` | 8초 | ✅ `abortSignal()` |
| `createSignedUrl()` | 5초 | ❌ SDK 미지원 → 대기만 끝냄 (요청은 런타임 기본 시간까지 남을 수 있음) |
| `info()` (대체 방식) | 5초 | ❌ 위와 같음 |
| `remove()` | 8초 | ❌ 위와 같음. 시간 초과 시 삭제 여부를 알 수 없어 `orphan` 가능으로 기록 |

- 진단 로그: 실패·시간 초과·대체 방식 사용 때만 `{ 단계, 결과, 소요 ms }` 를 남깁니다. 정상 처리(범위 요청 성공)에는 남기지 않습니다. secret 키·업로드 토큰·서명 URL·파일 경로는 기록하지 않습니다.

**해결한 문제 (2026-11-18)**: 처음 구현은 응답 스트림을 직접 읽고 `reader.cancel()` 을 기다렸는데, Next.js 서버 안에서만 서버 확인이 300초 이상 응답하지 않았습니다(Next.js 밖에서는 1초 이내 정상). 스트림 직접 읽기와 `cancel()` 대기를 없애고 범위 요청 응답(16바이트)만 읽도록 바꾼 뒤, 같은 파일 확인이 713~778ms 로 정상 동작했습니다.

## 동시성 위험 (해결되지 않음)

`removeUnusedImage` 는 "DB 에서 연결 여부 확인 → Storage 삭제" 두 단계입니다. Storage 삭제는 DB 트랜잭션에 넣을 수 없어서, **두 단계 사이에 다른 요청이 같은 경로를 상품에 연결하면 연결된 이미지 파일이 삭제될 수 있습니다.** 현재 구조에서는 이 경합을 막지 못합니다.

| 경합 상황 | 일으킬 수 있는 쪽 | 결과 | 현재 완화 |
|---|---|---|---|
| 저장 전 폐기 vs 같은 경로 저장 | 해당 `discardKey` 를 가진 탭 | 그 상품 이미지가 깨짐 | 화면은 저장 중·저장 후 폐기하지 않음, 서명 필요 |
| 수정 후 이전 이미지 정리 vs 그 경로를 다른 상품에 연결 | 누구나 (연결된 이미지 URL 은 공개) | 연결을 시도한 상품 이미지가 깨짐 | 저장 시 재검증, `unique(image_path)` |
| 상품 삭제 후 파일 정리 vs 같은 경로 연결 | 위와 같음 | 위와 같음 | 위와 같음 |
| 폐기 후 같은 업로드 허가로 재업로드 | 허가 토큰을 가진 탭 (2시간) | 미연결 파일이 다시 생김 | 앱 화면은 재업로드하지 않음 |

- 발생 빈도와 영향은 **측정·검증하지 않았습니다.** 위험 수준을 확정하지 않습니다.
- **공개 배포 전 재검토 필요**: 인증·사업장 권한(미션 7), DB 수준 동시성 보호(예: 삭제 예약 테이블 + 잠금, 연결·삭제 순서를 보장하는 DB 함수 · SQL 필요), 요청 횟수 제한(SQL 003 초안), 업로드·저장 대기 파일과 충돌하지 않는 고아 파일 정리.

> 원칙: **DB가 먼저, 파일 삭제는 나중.** 순서가 반대면 DB 저장이 실패했을 때 상품이 없는 이미지를 가리키게 된다.

## 보안

- 업로드 URL은 서버만 발급하고, 경로도 서버가 정한다. 덮어쓰기는 금지한다.
- `storage.objects`에는 공개 정책이 없다. 공개 키로는 업로드, 덮어쓰기, 삭제, 목록 조회를 할 수 없다. (2026-11-18 실제 확인)
- `image_path`는 그대로 믿지 않는다. 형식 검사와 매직 바이트 재검사를 거치고, DB UNIQUE 제약으로 다른 상품의 이미지를 가로챌 수도 없다.
- `discardImageUpload`(5-B)는 폐기 서명이 맞아도 상품에 연결된 파일은 지우지 않는다. 상품 삭제·수정 후 정리·검증 실패 정리도 같은 원칙의 `removeUnusedImage` 를 사용한다. 단, 연결 확인과 삭제 사이의 경합은 막지 못한다 ("동시성 위험" 절).
- 데모 이미지만 올리도록 업로드 칸에 안내한다.

**주의사항 (공개 URL·최적화)**
- 공개 URL 은 주소를 아는 누구나 볼 수 있다 (uuid 라 추측은 어렵지만 비밀은 아님).
- 사진 속 위치 정보(EXIF)는 제거하지 않는다. 데모 이미지만 사용하도록 안내로 대응한다.
- 파일을 지워도 Storage CDN 캐시(업로드 시 3600초 지정)와 Next.js 최적화 캐시(기본 4시간)에 한동안 남을 수 있다.
- 매직 바이트는 파일 앞부분만 확인한다. 서명 뒤에 다른 데이터를 붙인 파일이나 깨진 이미지는 통과할 수 있다 (허용 형식이 래스터 3종이고 SVG 불가라 위험은 낮음).
- Vercel 이미지 최적화와 Supabase 저장·전송량은 플랜 한도가 있으므로 배포 전에 확인한다.
